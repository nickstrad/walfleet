# Chapter 6 — Knowledge check answers

1. **Per-inode POSIX lock release and the three WAL stray-close outcomes (Experiment 6.1).**
   - **Why `stray-close db` kept `contender` blocked, while `stray-close -shm` admitted it:** POSIX advisory locks are tracked per `(process, inode)`. Closing any file descriptor to `lab.db` releases only that process's locks on `lab.db` — in WAL mode, the `SHARED` read lock (`bytes 1073741826-1073742335`). Writer exclusion in WAL mode lives on byte `120` (`WAL_WRITE_LOCK`) of the separate `-shm` file (`src/os_unix.c:4602`, `src/wal.c:294`). Only `stray-close -shm` releases `holder`'s `-shm` locks (`WAL_WRITE_LOCK`, `WAL_READ_LOCK`, and `DMS`), letting `contender` take byte `120`.
   - **The three WAL outcomes and `src/wal.c:3879`:**
     - **Part B (empty or fully checkpointed WAL, contender stays open):** `holder` started on `WAL_READ_LOCK(0)` (`pWal->readLock == 0`), so its `COMMIT` enters `walRestartLog` (`src/wal.c:3879`) and calls `walTryBeginRead(..., useWal=1)`. Every retry detects the changed `WalIndexHdr` (`src/wal.c:3261-3265`), loops `100` times (`WAL_RETRY_PROTOCOL_LIMIT`, `src/wal.c:2963`), and returns `SQLITE_PROTOCOL (15)` (`src/wal.c:3053-3056`). `contender`'s row survives and `holder` gets an error.
     - **Part C (WAL already holds uncheckpointed frames):** `holder` started on `WAL_READ_LOCK(1)` (byte `124`), so `if( pWal->readLock==0 )` at `src/wal.c:3879` is false and `walRestartLog` does not run. `holder` never re-checks the shared header, overwrites `contender`'s frames using its stale `mxFrame`, and both `COMMIT`s return `SQLITE_OK` while `contender`'s row silently disappears (`2 row(s): seed,holder`).
     - **Part D (contender closes and exits before `holder` commits):** Seeing no other locks on `.db` or `DMS`, `contender` closes as the last connection (`sqlite3WalClose`, `src/wal.c:2507-2571`) and unlinks `-wal` and `-shm`. `holder`'s `COMMIT` writes into its unlinked `-wal` descriptor and returns `SQLITE_OK`; when `holder` closes, only `holder`'s row survives and `contender`'s `SQLITE_OK` commit is silently lost.

2. **Why a deferred read-then-write skips `busy_timeout` (Experiment 6.2 C1–C3).**
   - In `btreeBeginTrans` (`src/btree.c:3740-3741`), the retry loop is:
     `while( (rc&0xFF)==SQLITE_BUSY && pBt->inTransaction==TRANS_NONE && btreeInvokeBusyHandler(pBt) )`.
   - In Parts C1 (`BEGIN IMMEDIATE`) and C2 (`BEGIN DEFERRED` whose first statement is an `INSERT`), the connection has not opened a transaction yet (`pBt->inTransaction == TRANS_NONE`), so `btreeBeginTrans` invokes `sqliteDefaultBusyCallback` (`src/main.c:1730-1792`) and waits up to `120,000ms` until `writer-1` commits.
   - In Part C3, `writer-2` ran `SELECT count(*) FROM lab` first, moving `inTransaction` to `TRANS_READ` (`!= TRANS_NONE`). When `writer-2` tries to upgrade to a write while `writer-1` holds `WAL_WRITE_LOCK`, `sqlite3WalBeginWriteTransaction` returns `SQLITE_BUSY (5)` and `btreeBeginTrans` exits immediately without calling the busy handler. Once `writer-1` commits, `sqlite3WalBeginWriteTransaction` (`src/wal.c:3734-3737`) sees that the shared `WalIndexHdr` no longer matches `writer-2`'s cached snapshot header and returns `SQLITE_BUSY_SNAPSHOT (517)` immediately; `writer-2` must `ROLLBACK` and restart (preferably with `BEGIN IMMEDIATE`).

3. **Rollback `PENDING` lock retention and WAL `locking_mode` boundaries (Experiment 6.2 A & D; stress test `BUSY-05b` under "What attacked this chapter").**
   - At step 56 in Part D, `writer`'s `COMMIT` needed an `EXCLUSIVE` lock on `.db`. In `unixLock` (`src/os_unix.c:1898-1905`), upgrading from `RESERVED` to `EXCLUSIVE` first write-locks `PENDING_BYTE` (`1073741824`) and then tries to write-lock the 510-byte `SHARED` range. Because `reader` still held `SHARED`, `EXCLUSIVE` failed with `SQLITE_BUSY (5)`, yet `writer` **kept `PENDING`**. Because every new `SHARED` lock must first read-lock `PENDING_BYTE`, `reader`'s new query at step 58 failed with `SQLITE_BUSY (5)` until `writer` retried `COMMIT` at step 59 and released all locks.
   - In WAL mode under default `PRAGMA locking_mode=NORMAL`, readers and writers never block each other, and `BEGIN EXCLUSIVE` behaves like `BEGIN IMMEDIATE` (taking only `-shm` byte `120`). Under `PRAGMA locking_mode=EXCLUSIVE`, however, `sqlite3PagerBegin` (`src/pager.c:5982-5988`) takes and keeps `.db`'s `EXCLUSIVE` lock on the first write, blocking other processes' readers with `SQLITE_BUSY (5)` at open (`BUSY-05b`).

4. **Why `nBackfill` advanced while `copy.db` kept step 5's page 1, and why replay fixed it (Experiment 6.4 Method 2).**
   - `walIteratorNext` (`src/wal.c:1764-1792`) yields each page in `-wal` **once**, at its newest frame number, and `walCheckpoint` (`src/wal.c:2312-2314`) copies that page into `.db` only when its newest frame is `<= mxSafeFrame` (the oldest active reader's mark). Because step 9 rewrote page 1 past frame `61` and step 12 rewrote page 1 past frame `116`, neither reader-limited `PASSIVE` checkpoint copied any version of page 1 into `.db`, even though other pages from steps 6–11 were copied and `nBackfill` advanced to `61` and `116`. Thus `.db` alone held a torn mixture of step-5 page 1 (`user_version 5`) and later pages (`10` integrity problems).
   - Because `capture` held its read transaction open across the copy, the WAL could not restart, so every committed frame from step 6 through step 13 (`167` frames, `92` distinct pages) stayed in `copy.wal`. Replaying all `167` frames onto `copy.db` with `walfile.ReplayFiles` overwrote every stale or torn page and extended the output to `124` pages (`507,904` bytes), producing an intact recipe step `13`.

5. **Three live-capture boundaries (stress tests `SNAP-05`, `SNAP-03b`, and `SNAP-04` under "What attacked this chapter").**
   - **Bare `BEGIN DEFERRED` (`SNAP-05`):** `sqlite3BeginTransaction` (`src/build.c:5245-5274`) emits no `OP_Transaction` for `BEGIN DEFERRED`, so no read transaction starts and no `WAL_READ_LOCK` is taken until a read statement runs. Without a read mark, `checkpoint(RESTART)` succeeds (`busy=0`) and the next commit restarts `-wal` with new salts, causing `.db` + `-wal` replay to fail with `SQLITE_CORRUPT (11)`.
   - **Holding `BEGIN IMMEDIATE` (`SNAP-03b`):** `BEGIN IMMEDIATE` takes `WAL_WRITE_LOCK` (`-shm` byte `120`), which blocks concurrent commits (`SQLITE_BUSY (5)`), but a `PASSIVE` checkpoint by another connection needs only `WAL_CKPT_LOCK` (byte `121`, not `WAL_WRITE_LOCK`). That `PASSIVE` checkpoint still runs and writes frames into `.db` mid-copy, tearing `.db` alone (`3` integrity problems); the capture succeeds only because `-wal` is copied afterward and replayed whole.
   - **Reader on a fully checkpointed WAL (`SNAP-04`):** When `nBackfill == mxFrame`, a new read transaction takes `WAL_READ_LOCK(0)` (byte `123`) and reads `.db` only. On the next commit, `walRestartLog` (`src/wal.c:3885`) acquires `WAL_READ_LOCK(1..4)` exclusively — not `WAL_READ_LOCK(0)` — so it restarts the WAL (`salt-1 + 1`, `nBackfill = 0`) underneath the open reader. The reader's snapshot stays safe because `walCheckpoint` (`src/wal.c:2254-2260`) requires `WAL_READ_LOCK(0)` exclusively before backfilling any page, but any WAL shipper that needs to prevent WAL restarts must pin a read mark while uncheckpointed frames exist in `-wal`.
