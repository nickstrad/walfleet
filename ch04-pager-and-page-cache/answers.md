# Chapter 4 — Knowledge check answers

1. **Cold versus hot journal across kills 1–25 and 26–46 (`synchronous=FULL`).** In `FULL` (and `NORMAL`) mode, `writeJournalHdr` (`src/pager.c:1495-1502`) writes the journal header's first 12 bytes (the 8-byte magic and 4-byte record count) as zeros. Until `syncJournal` writes the live magic (`0xd9...`) and record count (`7`) at offset 0 (`src/pager.c:4377-4410`, call #45 / kill 25), byte 0 is `0x00`. On reopen, `hasHotJournal` (`src/pager.c:5244-5251`) reads byte 0, sees `0x00`, treats the journal as cold, and ignores it without deleting it—which is safe because `t.db` is still untouched. From kill 26 onward, byte 0 is `0xd9`, so `hasHotJournal` reports a hot journal and `sqlite3PagerSharedLock` runs `pager_playback` and `pager_end_transaction`, rolling back the 7 journaled pages and unlinking `t.db-journal`. That pre-`COMMIT` cold window holds only because step 3 fits in the page cache (`spill=0`); if a transaction dirties more pages than `cache_size` holds, `pagerStress` calls `syncJournal` mid-transaction, activating the journal (`0xd9`) and writing pages to `t.db` before `COMMIT`.

2. **Reused freelist leaves and `PAGER_GET_NOCONTENT`.** Step 3's pre-step file (after step 2) had one freelist leaf—page `22`, zeroed by `secure_delete=ON`. When step 3 popped page 22 off the freelist, `allocateBtreePage` (`src/btree.c:6740`) fetched it with `PAGER_GET_NOCONTENT`, so `getPageNormal` (`src/pager.c:5645-5656`) set page 22's bit in `pInJournal` without writing a journal record for its unused bytes. Once the database write of page 22 completed (kill 32 lands on entry to offset `86016`, so kills 33–46 have page 22 written), hot-journal playback restored the freelist trunk page—returning page 22 to the freelist—without restoring page 22's zeros. Step 1's pre-step file (after step 0) had no freelist leaves, so every modified pre-existing page was journaled and every kill reopened to exact bytes. For step 3's 14 `b` outcomes (logically pre-step except reused freelist leaf `22`), the experiment verified `integrity_check` `ok`, identical 29-page file size, that every differing page (page `22`) belonged to the pre-step file's `dbfile.Census().FreelistLeaves` (from Chapter 2's `internal/dbfile`), and that `VACUUM INTO` matched pre-step's canonical SHA-256.

3. **Deleting a hot journal mid-write (E1) versus after the last database write (E3).**
   - **E1 (killed on entry to db write 10 of 18):** `t.db` is torn (30 pages: 9 differ from pre-step, 9 differ from post-step). Deleting `t.db-journal` prevents rollback, and reopening fails immediately with `database disk image is malformed (11)`.
   - **E3 (killed on entry to `sync t.db`):** All 18 dirty pages have reached `t.db`, so the file holds the complete post-step bytes, yet the writer died inside `COMMIT` and never acknowledged success to the application. With `t.db-journal` intact (kill 45 in Part D), SQLite rolls the transaction back to pre-step (`user_version=2`). Deleting `t.db-journal` silently turns that failed, unacknowledged transaction into a committed one (`user_version=3`, `accounts=21`, `documents=10`, `events=147`) while `PRAGMA integrity_check` returns `ok`, raising no error at all.

4. **Unified `PGroup` pooling, group ceiling, and the `~2x` RSS multiplier (Experiment 4.2 Part B).**
   - **Why connection 64 held 1,004 pages while connection 1 held 0:** `modernc.org/sqlite v1.60.1` is compiled with `SQLITE_ENABLE_MEMORY_MANAGEMENT=1`. In `pcache1Init` (`src/pcache1.c:718-719`), that sets `pcache1.separateCache = 0`, placing every connection's cache in one global `PGroup` with a single LRU list whose limit `nMaxPage` is the sum of all open connections' budgets (`pcache1Cachesize`, `src/pcache1.c:814-832`). When an active scanner reaches its own limit, `pcache1FetchStage2` (`src/pcache1.c:899-912`) recycles the group's least recently used page from idle connections, letting the active connection grow to all 1,004 pages of its file while idle connections drop to 0.
   - **First-pass sum versus true group ceiling:** On a single first-pass sweep across `N` connections, the sum equals `N × (nMax - 1)` (`64 × 482 = 30,848`). Under pool churn (Part D) or a second round-robin sweep across evicted connections (`nPage < nMax`), the group allocates up to its true cap `pGroup->nMaxPage = open × nMax` (`open × 483` at `-2000`), where `pcache1Unpin` (`src/pcache1.c:1096`) trims excess pages.
   - **Why RSS grew by about `255 MiB` for `128.3 MiB` of `CACHE_USED` (`1.99x` in one lab run; RSS is run-dependent):** `modernc.org/sqlite` allocates C heap memory through `modernc.org/memory` (its pure-Go C-heap allocator), whose power-of-two slot allocator rounds each ~4.3 KiB page allocation (`4,096` bytes + `PgHdr1` + extra) up into an `8 KiB` slot—nearly doubling physical memory per cached page.

5. **Memory-mapped reads in Experiment 4.2 Part E.** Setting `PRAGMA mmap_size=8224768` (twice the `4,112,384`-byte file) enables `getPageMMap` (`pagerFixMaplimit`, `src/pager.c:3579-3590`; `getPageMMap`, `src/pager.c:5687-5752`), which takes pointers straight into the OS `mmap` region through `sqlite3OsFetch` and wraps them in `pagerAcquireMapPage` handles outside `pcache1`. Those mapped pages are not counted in `SQLITE_DBSTATUS_CACHE_USED` (dropping it to `2` pages, or about `13,655` bytes in one lab run), yet faulting the file in still adds the file's size to the process's resident memory (about `+4.1 MiB` RSS). `/proc/self/status` proved the shift: file-backed memory (`RssFile`) grew by about `+4.0 MiB` while anonymous heap (`RssAnon`) grew by only about `+0.1 MiB` (run-dependent values printed by `course run`). In WAL mode, `getPageMMap` calls `sqlite3WalFindFrame` first (`src/pager.c:5719-5726`) and falls back to `getPageNormal` (copying into `pcache1`) for every page that has an uncheckpointed frame in `-wal`; `mmap` bypasses `pcache1` only for pages read from the main `.db` file.
