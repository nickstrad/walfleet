# Chapter 10 — Knowledge check answers

1. **Why `If-None-Match: *` alone is not enough (`resume-from-global-end` in Experiment 10.1).**
   - S3-compatible object stores like SeaweedFS cannot read an epoch number inside one object and compare it against another; `If-None-Match: *` enforces only **write-once key creation** (`PutIfAbsent`).
   - Single-writer fencing therefore requires two halves: slot exclusivity in S3 **plus** `fence.Adapter`'s writer rule ("list the chain, stop with `FencedError` if any slot holds a higher epoch, and append only at `end + 1` of your own validated chain").
   - In Experiment 10.1's `resume-from-global-end` self-test (matching raw `walship.Open` without `fence.Adapter`, and also demonstrated on live storage in stress test `MOD-03` under "What attacked this chapter" in Section 6), `If-None-Match: *` stays enabled, yet `170,698,606` of `11,458,358,774` interleavings violate an invariant. In the 7-step shortest counterexample, `B` fences at `1` and `A` takes over and fences at `2`. `B` then crashes, restarts by resuming at the store's global end (`2`), and puts its epoch-1 object into **free slot `3`**. Because slot `3` is unoccupied, `If-None-Match: *` accepts it, appending stale epoch-1 state after epoch `2`.

2. **Takeover vs relocation on `local-durable` writes, and why `SealSource` is separate from `FenceEpoch`.**
   - **Takeover (`Node.Claim`, Experiment 10.1):** Does not contact the old owner. It bumps the catalog epoch, restores the store's last shipped position (`position 2`, step `1`), and puts its fence snapshot at `position 3`. Any `local-durable` commit still sitting only on the old owner's disk (`user_version 2` from step `3`) was never shipped and is therefore lost (`in the store false`), which `local-durable` mode allows.
   - **Relocation (`relocate.Coordinator`, Experiment 10.3):** Performs a cooperative drain (`ShipFinal`, step `3`) on the source **before** the destination rebuilds and puts its fence snapshot. Every `local-durable` acknowledgement on the source reaches the store first and is preserved (`final user_version == acknowledged count` in all `32/32` cases; `Rollback` likewise seals and drains the source before re-claiming).
   - **Why `SealSource` (step `2`) is needed:** Bumping `databases.epoch` in the catalog (step `1`, `FenceEpoch`) does not stop the source node because a node does not read the catalog before handling `Write`. At step `1`'s boundary in Experiment 10.3, `a` still reports `owner at epoch 1, writable` and accepts the client's `local-durable` step `4`. Step `2` writes `<id>.sealed` so the cooperative source refuses further writes (`ErrSealed`) before step `3` drains it. Step `6` (`Activate`) then puts the store fence that stops any uncooperative source even if `.sealed` is removed (stress test `REL-05a` in Section 6).

3. **Why Experiment 10.2's `store-durable` kills landed on `catalog.db-wal` and recovered one step ahead of acknowledgements.**
   - A `store-durable` write in `Node.Write` executes three ordered steps before printing `ok write …`: (1) commit locally to `<id>.db-wal` at `synchronous=FULL` (`walFrames`, `src/wal.c:4195-4213`), (2) run `walship.Cycle` to PUT the segment to SeaweedFS S3 and run a `PASSIVE` checkpoint, and (3) call `Catalog.RecordShipped` to update `catalog.db`, which syncs `catalog.db-wal`.
   - Because updating `catalog.db` is the final `fsync`-heavy step after the segment is already durable in S3, `strace` kills at `fsync 29`, `57`, and `85` of `85` landed on `catalog.db-wal` during commands `4`, `8`, and `12` (`db-0004`). The node died before printing `ok write …`, so the client recorded `db-0004` at steps `0`, `1`, and `2`, even though `db-0004`'s new segment had already been accepted by SeaweedFS. When recovery deleted node `a`'s directory (`_work/10.2/node/a/` when run directly, or `/work/10.2/node/a/` inside the `lab` container) and rebuilt all four databases from S3 via `Claim`, `db-0004` rebuilt to steps `1`, `2`, and `3` (`recovered >= acknowledged`).

4. **Discontinuity snapshot shift on failed final put (case `22`) and finishing `rolled-back` before `Destination.Discard` (case `32` / `REL-04`).**
   - **Position `5` vs `4` with identical SHA-256 (`d53fc07b1293…`):** On a clean drain, `Node.evicted` runs `walship.Cycle`—shipping unshipped steps `3` and `4` as segment `4-5` and advancing the chain to position `5`—and then closes the shipper. When `fail-before-put` fires on `log/000000000004` (case `22`), the segment PUT fails, yet `c.shipper.Close()` still closes the last SQLite connection. `sqlite3WalClose` (`src/wal.c:2507-2571`) therefore checkpoints steps `3` and `4` into `db-0001.db` and deletes `-wal`. When `Resume` retries `Drain`, reopening finds no `-wal` and a file whose hash differs from slot `3`, so `walship` ships both commits together as a single **discontinuity snapshot** at slot `4` (`4-4 e1 snapshot`). The underlying database bytes are identical (`sha256 d53fc07b1293…`), so the destination's fence lands at position `5` instead of `6`.
   - **Why `FinishRelocation(..., RelocationRolledBack)` runs before `Destination.Discard`:** Once `source.Claim` puts the source's higher-epoch (`epoch 3`) fence snapshot in S3, the destination's leftover `<id>.staged` file is harmless: any attempt by `b` to `Activate` epoch `2` is rejected with `FencedError`. If `Rollback` called `Destination.Discard` first and failed while `b` was down (the bug exposed by stress test `REL-04` in Section 6), `catalog.databases` already said `owner=a, epoch=3` while `relocations.state` stayed `running`, blocking future relocations (`ErrRelocationRunning`) and turning retries into `superseded`. Recording `rolled-back` immediately after `source.Claim` and storing any discard failure in `Result.DiscardErr` lets `Rollback` finish cleanly even while `b` stays down (Experiment 10.3 case `32`).

5. **Zero WAL frames at quiesce and exact double-read count during Experiment 10.4's fleet rebuild.**
   - **`WAL frames found: 0`:** Before `TruncateAndHash` opens each file, `quiesce` sends `close` to all `8` writer processes. Closing each node closes `connmgr` and every open `walship.Shipper`. As the last SQLite connection to each database closes, `sqlite3WalClose` (`src/wal.c:2507-2571`) acquires `SQLITE_LOCK_EXCLUSIVE`, runs a `PASSIVE` checkpoint, and unlinks `-wal` and `-shm`. Every file is already cleanly at rest, leaving `0` WAL frames for `PRAGMA wal_checkpoint(TRUNCATE)`.
   - **`5,496` gets = `2 × 2,748` slots (`22,000` = `2 × 11,000` at `2,000` DBs):** For each database, `Node.Claim` creates a `fence.Adapter` and calls `adapter.Refresh`, which calls `fence.Chain` and `Get`s every existing slot to decode envelopes, verify lineage, and confirm no higher epoch exists. To keep open handles from retaining shipped bytes in RAM (stress test `CAT-05b` in Section 6), `Refresh` discards the raw object bytes. `Claim` then calls `n.imageAt` -> `walship.LoadCatalog`, which calls `adapter.Get` on every slot a second time to read the embedded `walship` objects and replay the image. Each pre-rebuild slot (`252 * 5 + 248 * 6 = 2,748` at `500` DBs; `1,000 * 5 + 1,000 * 6 = 11,000` at `2,000` DBs) is therefore fetched exactly twice.
