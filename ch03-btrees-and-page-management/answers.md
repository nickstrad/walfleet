# Chapter 3 — Knowledge check answers

1. **First split (4 pages) vs depth-2 append split (3 pages) vs `WITHOUT ROWID` append split (5 pages).** In Experiment 3.1 (4,096-byte pages, 1,000-byte blob rows, 4 rows per leaf in table `t`, WAL mode):
   - At insert `#5` (rowid `10`), table `t` has depth 1: root page `2` is itself the overflowing leaf. `balance()` (`src/btree.c:9130-9259`) first calls `balance_deeper` (`src/btree.c:9049-9094`), which allocates page `3`, copies root page `2`'s four cells and overflow cell to page `3`, and rewrites page `2` as an interior page pointing to page `3` so the root keeps page number `2`. On the next iteration of `balance()`'s loop, `balance_quick` (`src/btree.c:8007-8101`) splits page `3` by allocating leaf `4` for rowid `10` and adding divider `8` to root `2`. Updating page `1`'s in-header database size (`2 -> 4`) brings the total to `4` changed pages (`[1 2 3 4]`).
   - At insert `#9` (rowid `18`), the table is already at depth 2 and leaf `4` is the rightmost child of root `2`. `balance()` takes `balance_quick` alone, allocating page `5` for rowid `18`, inserting divider `16` into root `2`, and updating page `1`'s size (`4 -> 5`) without modifying full leaf `4`—exactly `3` changed pages (`[1 2 5]`).
   - In Experiment 3.1 Part E, `WITHOUT ROWID` stores rows in an **index B-tree** (`pPage->intKeyLeaf == 0`). Because `balance()`'s `balance_quick` guard (`src/btree.c:9185-9189`) requires `pPage->intKeyLeaf`, `WITHOUT ROWID` tables never use `balance_quick`. Their append splits always run `balance_nonroot` (`src/btree.c:8245-9027`), which redistributes cells across siblings and changes `5` pages at depth 2 instead of `3`.

2. **6 WAL frames vs 5 byte-changed pages on the middle split (Experiment 3.1 Part B).** Inserting rowid `11` into full leaf `4` calls `balance_nonroot` (`src/btree.c:8204-9027`), which gathers leaf `4` together with its left sibling (page `3`) and right sibling (page `5`) and calls `sqlite3PagerWrite` on every participating sibling page before editing or rebuilding them. After redistribution, page `3` still holds the same four cells (`2, 4, 6, 8`, SHA-256 `c0995adc833eadb1` before and after), but because the pager already marked page `3` writable, the commit appends page `3` to the write-ahead log (`-wal`) anyway—`6` frames `[1 2 3 4 5 8]` for `5` byte-changed pages `[1 2 4 5 8]`. For a replication platform, WAL shipping pays per page SQLite marks dirty (frames shipped `>=` pages changed), whereas a page-hash replicator (such as SQLite's `sqlite3_rsync`) compares page digests and skips unchanged pages like page `3`.

3. **`5` vs `54` WAL frames and `-wal` residue under `secure_delete=ON` (Experiment 3.2).**
   - Deleting `204` rows freed `50` pages: freelist trunk page `29` plus `49` freelist leaves. Under `secure_delete=OFF`, `freePage2` (`src/btree.c:6934-6935`) calls `sqlite3PagerDontWrite` (`src/pager.c:6329-6339`) on each freed freelist leaf so the pager omits those `49` pages from the commit entirely—writing only `5` WAL frames (page `1`, root `2`, trunk `29`, and the two partially emptied live leaves `27` and `78`). Under `secure_delete=ON`, `freePage2` (`src/btree.c:6864-6874`) zeroes all `4,096` bytes of every freed page and marks each writable, adding `49` frames for `54` WAL frames total.
   - `secure_delete=ON` zeroes pages in the database file (and writes zeroed page frames for the `DELETE`), but `-wal` is an append-only log: the earlier frames written by the `INSERT` stay intact in `-wal`. `PRAGMA wal_checkpoint(PASSIVE)` copies the zeroed frames back into `.db` without erasing `-wal`, so all `40` deleted rows remain readable in `-wal` until `PRAGMA wal_checkpoint(TRUNCATE)` resets the WAL file to zero bytes.

4. **WAL vs rollback batching and `backup`'s byte-43 canonical difference (Experiment 3.3 Parts A and A2).**
   - In rollback mode (`journal_mode=DELETE`, Part A2), every commit increments page `1`'s file change counter (bytes `24-27`) and version-valid-for (bytes `92-95`), so `one-transaction` ends at counter `3` and `per-statement` ends at counter `1463` (differing at **E1**, file SHA-256, on 1 of 266 pages; matching at **E2**, page-by-page comparison ignoring volatile header bytes `24-27`, `40-43`, and `92-99`, with differences only at `[26 27 94 95]`). In WAL mode (`Part A`), page `1`'s change counter is written only when page `1` is dirty and holds `dbFileVers + 1` (the pager's cached change counter plus one). Append-only inserts into `accounts`, `documents`, and `events` leave no other trace of commit boundaries, so `one-transaction` and `per-statement` produce byte-identical files (`224810279caf4016`).
   - When `sqlite3_backup_step` (`src/backup.c:448`) finishes copying R0 (the deterministic 30-step test database) into an empty destination file, it sets the destination's schema cookie to `old destination cookie + 1 = 1` (while R0's schema cookie is `4`). `sqlite3RunVacuum` (`src/vacuum.c:143-427`) copies the source's schema cookie incremented by `+1`, producing schema cookies `5` (R0) and `2` (backup). The two `VACUUM INTO` canonical files therefore differ at byte `43` only (`E1` differ, `E2` equal).

5. **Three `dbhash` blind spots and how `internal/equal/logical.go` closes them (Experiment 3.3 Part B).** Any three of these five blind spots of `dbhash` (SQLite's bundled C content-hashing utility, `tool/dbhash.c:281-360` and `tool/dbhash.c:379-491`), compared against `internal/equal/logical.go` (this repository's E3 logical hasher):
   - **Implicit rowids (`1,2` vs `5,9`):** `dbhash` runs `SELECT * FROM t` without selecting `rowid`, so hidden rowids never enter its hash. `logical.go` (`TableSelect`) explicitly selects and orders by the rowid alias (`rowid`, `_rowid_`, `oid`, or an `INTEGER PRIMARY KEY` fallback) for every rowid table.
   - **`sqlite_sequence` (`1` vs `2`):** `dbhash` skips every table whose name starts with `sqlite_`. `logical.go` (`logicalTables`) walks every `table` and `shadow` table in `main` from `pragma_table_list` except `sqlite_schema` (already hashed by `walkSchema`), which includes `sqlite_sequence` and `sqlite_stat*`.
   - **`user_version` (`1` vs `2`):** `dbhash` hashes no database-header pragmas. `logical.go` hashes all seven persistent pragmas in `LogicalPragmas` (`page_size`, `encoding`, `auto_vacuum`, `user_version`, `application_id`, `journal_mode`, `default_cache_size`).
   - **Value boundary (`'a3','b'` vs `'a','3b'`):** `hash_one_query` writes type tag `'3'` followed by raw UTF-8 bytes with no length prefix, hashing `"3a33b"` for both rows. `logical.go` (`streamEncoder`) writes a 1-byte tag (`'T'`/`'B'`) followed by an 8-byte big-endian byte length before every TEXT or BLOB value.
   - **Row moved between tables:** `hash_one_query` writes no row or table delimiter and omits table names from the row stream. `logical.go` wraps every table with a `'T'` header (name, rowid flag, column count, column names), prefixes every row with `'R'` + value count, and closes each table with `'E'` + row count.
