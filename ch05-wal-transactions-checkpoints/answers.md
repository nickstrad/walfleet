# Chapter 5 — Knowledge check answers

1. **Deterministic WAL comparison and `walDecodeFrame` checksum span (Experiment 5.1).**
   - **Differing regions:** Between two runs of the exact same workload, the two `387,312`-byte WAL files differ only in `header salts`, `header checksum`, `frame salts`, and `frame checksums` (a run-dependent count of bytes printed by `course run`: `1,519` in one lab run). Every magic, version, page-size, checkpoint-sequence, frame page-number, frame commit-size, and page-data byte is identical, and the `(page, page sha256, commit size)` tuple sequences match across repeated runs and across `synchronous=FULL`, `NORMAL`, and `OFF`.
   - **What `walDecodeFrame` checksums:** `walDecodeFrame` (`src/wal.c:1038-1039`, matching `walEncodeFrame` at `src/wal.c:985-986`) feeds only the **first 8 bytes** of the 24-byte frame header (`pgno` and `commit-size`) plus the `pageSize`-byte page image into `walChecksumBytes`—excluding the 8 salt bytes (`8..15`) and the 8 stored checksum bytes (`16..23`). The comment directly above line 1038 (`src/wal.c:1033`) mistakenly says "the first 16 bytes of this frame-header", contradicting both the code and the top format comment (`src/wal.c:65-68`).

2. **Spilled frames after rollback, disposable `-shm`, and stale-generation bases (Experiment 5.2).**
   - **Frames `42–60` after `ROLLBACK`:** Rolling back does not shrink or erase `-wal`. The file stays `247,232` bytes (`60` frames, all checksum-valid), while `-shm` keeps `mxFrame = 41` (the last committed frame). Both `walfile.Replay` and SQLite stop at `LastCommitFrame` (`41`) and ignore frames `42–60` because no commit frame follows them.
   - **Why missing and stale `-shm` give the same `fb68a521…`:** `-shm` is pure derived state. When the first connection opens a WAL database, the unix VFS takes the dead-man-switch lock (`UNIX_SHM_DMS`, `-shm` byte 128), truncates `-shm`, and runs `walIndexRecover` (`src/wal.c:1390-1614`) to rebuild the wal-index directly from `-wal`. Even a valid-looking `-shm` copied from Part A (`mxFrame = 155`, different salts) is discarded and rebuilt.
   - **Why raw `Replay` cannot detect a stale-generation base:** The `.db` file header stores no WAL salt or generation identifier, and the WAL header stores only its own salts and per-connection checkpoint sequence. Without external capture metadata pairing a base SHA-256 with the WAL generation it matches (Chapter 9's `internal/walship`), applying a generation-2 WAL onto a generation-0 base succeeds with `err == nil` and produces a corrupt database (`REP-02`).

3. **Part A read marks vs Part B `WAL_READ_LOCK(0)` and stale marks (Experiment 5.3).**
   - **Part A (`nBackfill = 0 < mxFrame = 22`):** `walTryBeginRead` (`src/wal.c:3182-3205`) writes `22` into `aReadMark[1]` and holds a shared lock on `WAL_READ_LOCK(1)`. Checkpoints cannot copy frames past the lowest locked mark (`mxSafeFrame` caps at `22`), and `walRestartLog` cannot reset the WAL while any lock in `1..4` is held, so the WAL grows to `555` frames (`2,286,632` bytes).
   - **Part B (`nBackfill = 22 == mxFrame = 22`):** Because every frame is already in `.db`, `walTryBeginRead` (`src/wal.c:3134-3163`) takes `WAL_READ_LOCK(0)` shared, leaves `aReadMark[1..4]` untouched, and reads only `.db`. On step 7, `walRestartLog` (`src/wal.c:3885`) only needs exclusive locks on `WAL_READ_LOCK(1..4)`, so it restarts the WAL immediately (`salt-1 + 1`, `mxFrame = 16`). However, `walCheckpoint` (`src/wal.c:2259-2260`) must take `WAL_READ_LOCK(0)` exclusively before copying a single page to `.db` (so it cannot overwrite pages the `.db`-only reader is reading); therefore `nBackfill` stays `0` through step 30 (`533` frames, `2,195,992` bytes).
   - **Why `aReadMark[1]` still shows `22` after the reader ends in Part A:** Ending a read transaction only releases the POSIX shared lock on `WAL_READ_LOCK(1)` without clearing `aReadMark[1]`. The value remains in `-shm` until a checkpoint or new reader takes `WAL_READ_LOCK(1)` exclusively and overwrites it.

4. **`RESTART`/`TRUNCATE` against a current reader and cross-connection `TRUNCATE` salts (Experiment 5.4).**
   - **Why `RESTART`/`TRUNCATE` return `busy=1` on `"reader current"`:** A reader at frame `38` does not restrict copying frames `1..38` into `.db`, so `PASSIVE` and `FULL` finish with `nBackfill = 38` and return `busy=0`. After backfilling, however, `RESTART` and `TRUNCATE` (`src/wal.c:2363-2388`) also try `walBusyLock` on `WAL_READ_LOCK(1..4)` so no reader remains attached to the WAL (ensuring the next write can restart at frame 1, or allowing `TRUNCATE` to zero the file). The current reader still holds `WAL_READ_LOCK(1)`, so both wait out `busy_timeout` and return `busy=1`.
   - **Why cross-connection vs same-connection `TRUNCATE` differs:** When connection C runs `TRUNCATE`, `walRestartHdr` (`src/wal.c:2156`) increments C's own `pWal->nCkpt` and writes `salt-1 + 1` into `-shm`, then truncates `-wal` to 0 bytes. When writer W writes the next WAL header (`iFrame == 0`), `walFrames` (`src/wal.c:4095-4096`) writes W's own `pWal->nCkpt`—which is still `0`—and because `pWal->nCkpt == 0`, calls `sqlite3_randomness(8, pWal->hdr.aSalt)`, producing fresh random salts and `checkpoint-seq = 0`. When W runs `TRUNCATE` itself, W's own `pWal->nCkpt` is `1`, so `walFrames` skips re-randomization and writes `salt-1 + 1` and `checkpoint-seq = 1`.

5. **WAL sync flags, the reversed `pager.c` comment, and `wal_autocheckpoint=0`.**
   - **`NORMAL` vs `FULL` syncs:** `src/wal.h:25-26` defines `WAL_SYNC_FLAGS(X) = (X)&0x03` (commit sync) and `CKPT_SYNC_FLAGS(X) = ((X)>>2)&0x03` (checkpoint and fresh WAL-header sync). `sqlite3PagerSetFlags` (`src/pager.c:3692-3695`) puts `syncFlags << 2` into `walSyncFlags` and ORs `syncFlags` into the low two bits only when `fullSync` is true (`FULL` or `EXTRA`). Thus `NORMAL` syncs at checkpoints (and fresh WAL headers) with **zero** steady-state commit syncs, whereas `FULL` also syncs `-wal` on every commit.
   - **Comment bug:** `src/pager.c:607-617` states the bitfields backwards, claiming the low two bits are for checkpoints and bits `0x04`/`0x08` are for commits.
   - **Why set `wal_autocheckpoint=0` on application connections:** `sqlite3WalDefaultHook` (`src/main.c:2484-2496`) runs a `PASSIVE` checkpoint inside any committing connection once the WAL reaches 1,000 frames, and any complete backfill allows the next write to restart the WAL at frame 1 (Experiment 5.4). A WAL-shipping platform must disable autocheckpoint on application connections and drive checkpoints itself so WAL generations never wrap before frames are shipped.
