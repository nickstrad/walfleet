# Chapter 2 — Knowledge check answers

1. **In-header database size trust rule.** Both `lockBtree` ([`src/btree.c:3298-3302`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/btree.c#L3298-L3302)) and `internal/dbfile` (Chapter 2's pure-Go file parser) trust the 4-byte page count at header offset 28 only when it is non-zero **and** bytes 24–27 (file change counter) equal bytes 92–95 (version-valid-for). On Experiment 2.1 Part E's edited copies of a 39-page rollback-mode database (`size-base.db`), when offset 28 is `0` (E4) or bytes 24–27 disagree with bytes 92–95 (E2), both ignore offset 28 and compute the page count from the OS file size (`39` pages). When the counters agree and offset 28 exceeds the OS file size (`44` vs `39` pages in E3), both treat the file as corrupt (`lockBtree`, [`src/btree.c:3405-3412`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/btree.c#L3405-L3412)): SQLite returns `database disk image is malformed (11)`, and `internal/dbfile` returns `ErrCorrupt`.

2. **WAL-mode header change counter behavior.** Experiment 2.1 Part C starts from a WAL-mode database built to step 27 (file change counter `29`) and runs either recipe steps 28–30 (each updating `PRAGMA user_version` on page 1) or three `UPDATE accounts` statements:
   - **One connection, three page-1 commits (C1):** `pagerWalFrames` ([`src/pager.c:3264`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/pager.c#L3264)) calls `pager_write_changecounter` ([`src/pager.c:3130-3143`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/pager.c#L3130-L3143)), which writes `dbFileVers + 1` rather than the page's current counter + 1. Because `dbFileVers` refreshes only when `readDbPage` reads page 1 from storage ([`src/pager.c:3093-3110`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/pager.c#L3093-L3110)), keeping page 1 in that connection's page cache means it reads `29` once and writes `30` on steps 28, 29, and 30. `.db` stays at `29` until the close checkpoint copies `30` into it.
   - **One connection with `PRAGMA shrink_memory` before each step (C4):** Dropping unused pages from the connection's cache evicts page 1 between commits, forcing `readDbPage` to re-read page 1 from `-wal` and refresh `dbFileVers` before each step (`29 -> 30`, `30 -> 31`, `31 -> 32`). This proves C1's flat counter is a page-cache effect, not a per-connection rule.
   - **Three `UPDATE accounts` commits (C2):** None of those commits dirty page 1, so page 1 is absent from the dirty-page list and `pagerWalFrames` never calls `pager_write_changecounter`. Every header byte remains unchanged both in `-wal` and in `.db` after checkpoint.
   - **New connection per step (C3):** Each new writer opens the database and calls `readDbPage` on page 1 from the latest WAL frame, refreshing `dbFileVers` each time (`29 -> 30`, `30 -> 31`, `31 -> 32`)—one way to trigger a re-read of page 1 rather than the underlying rule itself.

3. **Local/overflow payload split (Experiment 2.2 part B).** With a 4,096-byte page size and 0 reserved bytes (`usableSize = 4096`), a table leaf has `maxLocal = 4061`, `minLocal = 489`, and `4092` payload bytes per overflow page:
   - Payload `4061` (`<= maxLocal`): `4061` bytes local, `0` overflow pages.
   - Payload `4062` (`> maxLocal`): `489` bytes local, `1` overflow page carrying `3573` bytes.
   - Payload `8153` (`> maxLocal`): `4061` bytes local, `1` overflow page carrying `4092` bytes (completely full).
   - **Why `4062` drops to `489`:** `btreeParseCellAdjustSizeForOverflow` ([`src/btree.c:1178-1207`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/btree.c#L1178-L1207)) computes `surplus = minLocal + (P - minLocal) % (usableSize - 4)`. For `P = 4062`, `surplus = 489 + (4062 - 489) % 4092 = 4062`, which exceeds `maxLocal` (`4061`), so the formula falls back to `minLocal` (`489`). For `P = 8153`, `surplus = 489 + (8153 - 489) % 4092 = 489 + 3572 = 4061 <= maxLocal`, keeping `4061` local so the single overflow page holds an exact `4092` bytes with zero wasted space.

4. **Truncated last page (Experiment 2.2 part F2).** Experiment 2.2 Part F starts from a 6-page (24,576-byte) rollback-mode database whose page 6 is an unused freelist leaf; F2 cuts page 6 from 4,096 to 2,048 bytes (`22,528` bytes total). SQLite rounds the OS file size up to whole pages (`6` pages, matching the in-header size `6`), accepts the short read in `readDbPage` ([`src/pager.c:3088-3090`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/pager.c#L3088-L3090)), and zero-fills the trailing half-page. Because page 6 is a freelist leaf whose contents are not checked, `PRAGMA integrity_check` returns `ok`. `internal/dbfile` (Chapter 2's pure-Go parser) refuses any file whose size is not an exact multiple of `pageSize` with `ErrTruncated`, because a page-based capture could not faithfully rebuild a partial page.

5. **Not-at-rest captures and hot-journal creation (Experiment 2.3 part D).** Each scenario starts a 6-step database (`r.db`) and spawns a child process that leaves the database not at rest and exits without closing its connection:
   - **D1 (WAL mode):** The child commits a `+1000` balance `UPDATE` on account 1 (moving it from `43047` to `44047`). Capturing `r.db` alone while `-wal` holds 4,152 bytes of committed frames produces a stale database that silently loses that committed `UPDATE` (account 1 balance `43047` instead of `44047`).
   - **D2 (rollback mode):** The child updates all 17 `documents` bodies to zeroed blobs (`zeroblob(length(body))`) inside an uncommitted transaction and exits before `COMMIT`. Capturing `r.db` alone beside the 203,312-byte hot `-journal` captures a torn, uncommitted state (`17 rows, 15 bodies all zero`) that no transaction ever committed; opening with SQLite rolls the journal back to `0 bodies all zero`.
   - **Why D2 needed `cache_size=10`:** Under `synchronous=FULL` or `NORMAL`, SQLite initializes a rollback journal with zeroed magic bytes ([`src/pager.c:1494-1501`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/pager.c#L1494-L1501)) and writes the live magic only when syncing the journal ([`src/pager.c:4377`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/pager.c#L4377))—either at `COMMIT` or when dirty pages spill from the page cache to `.db` mid-transaction. Setting `cache_size=10` and updating all 17 document bodies forced a cache spill and journal sync before `COMMIT`, leaving both modified pages in `r.db` and a live hot journal on disk when the child exited.
