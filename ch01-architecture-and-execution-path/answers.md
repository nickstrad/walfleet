# Chapter 1 — Knowledge check answers

1. **Schema change between `Prepare` and `Step`.** SQLite's `sqlite3_prepare_v2` ([`src/prepare.c:937-954`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/prepare.c#L937-L954)) passes `SQLITE_PREPARE_SAVESQL` to `sqlite3LockAndPrepare`, which saves the original SQL text on the prepared statement (`sqlite3VdbeSetSql` at [`src/prepare.c:795`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/prepare.c#L795)). When `sqlite3_step` ([`src/vdbeapi.c:919-966`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/vdbeapi.c#L919-L966)) runs the statement, `OP_Transaction` ([`src/vdbe.c:4102-4201`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/vdbe.c#L4102-L4201)) compares the database file's schema cookie against the cookie compiled into bytecode operand `P3`, finds a mismatch, and expires the statement with `SQLITE_SCHEMA`. `sqlite3_step` catches `SQLITE_SCHEMA` in a loop up to `SQLITE_MAX_SCHEMA_RETRY` (`50`, [`src/vdbeInt.h:26`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/vdbeInt.h#L26)) times, calls `sqlite3Reprepare` to recompile from the saved SQL text, resets the statement, and steps it again automatically.

2. **`pwrite64` calls on `t.db` in rollback mode vs WAL mode.** In Experiment 1.2 (inserting one row into a two-page database `t.db`, where page 1 holds the 100-byte header and `sqlite_schema` and page 2 is table `t`'s leaf page):
   - **Rollback mode (`journal_mode=delete`):** `2` `pwrite64` calls hit `t.db`: `off=0 len=4096` (page 1, updated change counter and version-valid-for) and `off=4096 len=4096` (page 2, table `t`'s leaf page holding the new row). Before those writes, SQLite journals the original images of both pages into `t.db-journal` and syncs both the journal and directory `.`.
   - **WAL mode (`journal_mode=wal`):** `0` `pwrite64` calls hit `t.db`. SQLite writes the 32-byte WAL header (`t.db-wal off=0 len=32`), syncs `t.db-wal` and `.`, appends frame 1's 24-byte header (`off=32 len=24`) and page 2's 4,096-byte image (`off=56 len=4096`) to `t.db-wal`, and syncs `t.db-wal`. Page 2's new bytes reach `t.db` only later during a checkpoint.

3. **Extra syscalls in the Go driver's twin check and the `ANALYZE` limit.** Experiment 1.2's twin check runs the same `INSERT` under `strace` in both the pure-Go `modernc.org/sqlite` driver and SQLite's C `sqlite3` CLI. `modernc.org/sqlite` links `modernc.org/libc` (`v1.77.1`), whose musl-derived `open()` issues an explicit `fcntl(fd, F_SETFD, FD_CLOEXEC)` after opening a file with `O_CLOEXEC`. SQLite's C build relies on `O_CLOEXEC` directly in `robust_open` ([`src/os_unix.c:867-869`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/os_unix.c#L867-L869)). That produced `2` extra `fcntl F_SETFD` calls in rollback mode (`t.db-journal` and `.`) and `1` in WAL mode (`.`). Because `F_SETFD` only sets the close-on-exec flag on a process-local file descriptor, it writes nothing to disk and touches no POSIX byte-range locks; every write, sync, read, lock, open, unlink, and close matched identically, and both builds left byte-identical files. Where compile options differ between the builds—such as `ENABLE_STAT4` enabled in the Go driver and absent in the CLI—running `ANALYZE` on an indexed table creates `sqlite_stat4` only in the driver, causing the two builds to diverge and write different files.

4. **Connection sessions in WAL mode vs rollback mode.** Experiment 1.3 Variant 6 compares building steps 0–6 of the seeded `internal/recipe` workload (7 commits total) with one fresh connection per step against one long-lived connection for all 7 steps. In WAL mode, only `2` bytes differed—page 1 bytes `27` and `95`, the low bytes of the 4-byte file change counter (bytes 24–27) and version-valid-for field (bytes 92–95). In WAL mode, `pagerWalFrames` ([`src/pager.c:3264`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/pager.c#L3264)) calls `pager_write_changecounter` ([`src/pager.c:3130-3143`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/pager.c#L3130-L3143)) only when a commit dirties page 1 (`pList->pgno == 1`), writing `dbFileVers + 1`. SQLite refreshes `dbFileVers` only when page 1 is read from storage via `readDbPage` ([`src/pager.c:3109-3110`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/pager.c#L3109-L3110))—on a new connection or after page-1 cache eviction (such as `cache_size=0`)—not after a WAL commit. Because every recipe step runs `PRAGMA user_version = k` and dirties page 1, one long-lived connection wrote the same counter across all 7 commits, whereas one connection per step incremented it each session. Commits that never dirty page 1 (such as updating a row in `accounts`) leave WAL files `identical` across sessions. In rollback mode, the change counter increments on every commit regardless of session count, so both builds ran 7 commits and produced `identical` files.

5. **Transaction batching with `secure_delete=ON`, `OFF`, and `FAST` in WAL mode.** Experiment 1.3 Variant 4 compares committing steps 0–6 of `internal/recipe` one step per transaction against merging steps `2+3` and `4+5` on one WAL connection. On a single WAL connection, the header change counter does not depend on commit count. With `secure_delete=OFF`, deleting rows in step 3 that step 2 inserted left stale deleted bytes inside unused regions of B-tree leaf pages (the unallocated gap between the cell-pointer array and cell content area, plus freeblocks)—`357` bytes on page `24` and `1,207` bytes on page `28`—so merging steps `2+3` and `4+5` changed which stale bytes remained. Enabling `secure_delete=ON` zeroes freed space inside B-tree pages and on freed freelist pages ([`src/btree.c:6864-6874`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/btree.c#L6864-L6874)), removing those history-dependent bytes so both batchings were `identical`. `secure_delete=FAST` sets `BTS_OVERWRITE` without `BTS_SECURE_DELETE` ([`src/btree.c:3181-3194`](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/btree.c#L3181-L3194)), zeroing freed space inside B-tree pages while leaving stale bytes on freed freelist pages (`29`, `36`, and `37` in Experiment 1.3), and at 30-step scale `FAST` re-exposes batching divergence (adversarial test `DET-05d`).
