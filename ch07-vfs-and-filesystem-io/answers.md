# Chapter 7 — Knowledge check answers

1. **3 `xSync` VFS calls vs 4 sync syscalls in rollback `DELETE` mode at `FULL`.** At `synchronous=FULL`, `syncJournal` (`src/pager.c:4332-4441`) calls `xSync` on `t.db-journal`, rewrites the 12-byte journal header, and calls `xSync` on `t.db-journal` a second time; `sqlite3PagerCommitPhaseOne` (`src/pager.c:6511-6730`) then writes the dirty pages to `t.db` and calls `xSync` on `t.db`—totaling 3 `xSync` VFS calls (`2` on `-journal`, `1` on `.db`). However, when `unixOpen` creates a new journal (`isNewJrnl`, `src/os_unix.c:6569-6572`), it sets `UNIXFILE_DIRSYNC` in `ctrlFlags` (`src/os_unix.c:6777`). Inside the first `unixSync` on that journal (`src/os_unix.c:3941-3953`), SQLite syncs the journal file, then opens the parent directory (`.`), syncs it so the new journal's directory entry survives power loss, closes the directory, and clears `UNIXFILE_DIRSYNC`. The second journal `xSync` therefore syncs only `t.db-journal`. Because `DELETE` mode unlinks and recreates the journal on every write transaction, every commit pays that one-time directory sync (`2 + 1 + 1 = 4` sync syscalls).

2. **Per-commit syncs in WAL mode at `synchronous=NORMAL` (`1000 x 1` commits, `wal_autocheckpoint=1000`).** Out of the 1,000 commits:
   - **998 commits** performed **0 syncs** `[-]`, because at `synchronous=NORMAL`, `sqlite3PagerSetFlags` (`src/pager.c:3685-3698`) leaves the low commit-sync bits of `walSyncFlags` zero.
   - **1 commit** performed **2 syncs** `[db:1 wal:1]` (with database writes): when the WAL reached 1,000 frames, the automatic checkpoint ran `walCheckpoint` (`src/wal.c:2199-2395`), which synced `t.db-wal` before copying pages back (`src/wal.c:2277`) and synced `t.db` after copying them (`src/wal.c:2333`), both under `CKPT_SYNC_FLAGS` (active at `NORMAL` and `FULL`).
   - **1 commit** (immediately after the checkpoint commit) performed **1 sync** `[wal:1]`: finding the WAL fully checkpointed with no blocking reader, `walRestartLog` (`src/wal.c:3875-3915`) reset the WAL to frame 0 with a new salt, wrote a fresh 32-byte WAL header, and synced it via `syncHeader` (`src/wal.c:4114-4124`, also under `CKPT_SYNC_FLAGS`).

3. **Why `-vfstrace` prints `FULL` while `govfs` records `0x2 (NORMAL)`.** In `src/sqlite.h.in:731-733`, `SQLITE_SYNC_NORMAL` is `0x02` and `SQLITE_SYNC_FULL` is `0x03`, so `SQLITE_SYNC_FULL` contains `SQLITE_SYNC_NORMAL`'s bit. `vfstraceSync` (`ext/misc/vfstrace.c:453-454`) tests `if (flags & SQLITE_SYNC_FULL)` instead of comparing `(flags & 0x0F) == SQLITE_SYNC_FULL` as `unixSync` does (`src/os_unix.c:3916`). Because `0x02 & 0x03` is nonzero, `vfstrace` labels every `NORMAL` sync as `FULL`. In default settings, `PRAGMA synchronous=FULL` increases the *number* of `xSync` calls rather than changing the sync flag; `sqlite3PagerSetFlags` (`src/pager.c:3687-3688`) passes `SQLITE_SYNC_FULL` (`0x03`) only when `PRAGMA fullfsync=ON` is set.

4. **Where faults surfaced in WAL vs `DELETE` mode, and why failing WAL `xSync #2` still rolled back.**
   - In **WAL mode**, modified pages stay in the connection's page cache until `COMMIT`, when `walFrames` (`src/wal.c:4038-4266`) writes all 25 frames (51 `xWrite` calls including the WAL header) and runs the 2 `xSync` calls; every one of the 53 faults therefore surfaced at `COMMIT`. In **`DELETE` mode**, the pager writes a page's original image to `t.db-journal` as soon as a statement first dirties that page, so the first 40 `xWrite` faults surfaced during statements 1, 5, 9, 54, and 55 (while journal header rewrite `#41`, database writes `#42`–`#66`, and all 3 `xSync` calls surfaced at `COMMIT`).
   - When **WAL `xSync #2`** (the commit sync) failed with `SQLITE_IOERR`, `walFrames` aborted before publishing the updated WAL-index header (`mxFrame`) in `-shm`. Because the new frames were never made visible in the WAL-index, closing the connection checkpointed only up to the previous committed end (frame 0) and deleted `t.db-wal`, leaving exact step-3 bytes (`user_version=3`, marker row absent, `integrity ok`).

5. **Opening a WAL-format snapshot through `modernc.org/sqlite/vfs`.**
   - **Without `immutable=1` (no parameters or `mode=ro`):** Opening fails with `SQLite error code 14 (SQLITE_CANTOPEN)` after 5 requests (`stat snapshot.db`, 100-byte header, `stat` `-journal` and `-wal`, page 1). SQLite reads header bytes 18–19 = `2` (WAL format), requires shared memory (`io_methods` version ≥ 2) to open WAL mode, and fails because `modernc.org/sqlite/vfs` registers version 1 (`xShm*` absent).
   - **Flipping header bytes 18–19 from `2` to `1`:** With bytes 18–19 set to `1` (rollback format), `snapshot-rollback.db` opens with no parameters and returns the exact same data (`user_version=30 events=1177`), proving the header's WAL flag—not the page content—demands shared memory. However, omitting `immutable=1` doubles the request count from **8 requests** (`1` stat, `7` range, `24,676` bytes) to **16 requests** (`7` stat, `9` range, `24,708` bytes), because every read transaction probes `-journal` (3 times) and `-wal` and re-reads the 16-byte change counter (`bytes 24-39`), and rewriting header bytes breaks the file's E1 SHA-256 hash.
   - **Uncheckpointed database with `immutable=1`:** Publishing `live.db` (step 29) alongside `live.db-wal` (holding committed step 30 in 30 frames) and reading with `immutable=1` silently returns the stale step-29 state (`user_version=29 events=1130`) with no error and 0 requests naming `live.db-wal`, because `immutable=1` makes the pager skip all locking and sidecar checks (`src/pager.c:5033-5056`). For the same reason, overwriting a served snapshot object in place while an `immutable=1` connection stays open mixes cached old pages with new pages and produces `SQLITE_CORRUPT` (`11`, `src/sqlite.h.in:3922-3929`).
