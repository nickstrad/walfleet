# Chapter 9 — Knowledge check answers

1. **`sqlite3_backup_remaining`, same-connection commits vs rollbacks, and external commits.**
   - `sqlite3_backup_step` (`src/backup.c:428-429`) recomputes `p->nRemaining = nSrcPage + 1 - p->iNext` from the source database's **current** page count on every step. When the backup's own connection committed steps `11` and `12`, the database grew from `100` to `108` to `118` pages, so `remaining` rose (`90 -> 93 -> 98`) even though `iNext` kept advancing by `5` pages per step (`copied = pagecount - remaining` went `5, 10, 15, 20, 25`).
   - Same-connection **commits** do not restart the backup because `pagerWalFrames` (`src/pager.c:3270`) calls `sqlite3BackupUpdate` (`src/backup.c:688-715`), which re-copies any modified page with `iPage < p->iNext` directly into the destination and leaves `iNext` unchanged.
   - When the **writer child** committed step `13`, the source pager detected an external change at the start of step `6`'s read transaction and called `pager_reset` (`src/pager.c:1783-1787`), which called `sqlite3BackupRestart` (`src/backup.c:728-734`) and reset `p->iNext = 1` (`copied` dropped back to `5`).
   - A same-connection write followed by **`ROLLBACK`** (stress test `CAP-03a` under "What attacked this chapter" in Section 6) also calls `sqlite3BackupRestart` (`src/pager.c:3185`) in WAL mode, resetting `iNext = 1` (`[5 10 5 10]`), because the pager cannot rely on forward page updates to undo arbitrary rolled-back state in the destination.

2. **Backup API's `E1-after-VACUUM-INTO no` and `VACUUM INTO`'s `E3` result.**
   - On completion, `sqlite3_backup_step` (`src/backup.c:448`) sets the destination's schema cookie (header bytes `40–43`) to `p->iDestSchema + 1`—the **destination's** old cookie plus `1`, not the source's cookie. For a fresh destination file (`iDestSchema = 0`), the backup gets schema cookie `1` while the step-6 source has schema cookie `4` (contributing byte `43` alongside bytes `27` and `95` in the E2 diff). When `VACUUM INTO` runs on both files, `sqlite3RunVacuum` (`src/vacuum.c:359`) copies `BTREE_SCHEMA_VERSION` and adds `1`, producing canonical files with cookies `2` vs `5`—which still differ at byte `43`.
   - `VACUUM INTO` (`src/vacuum.c:143-427`) attaches a brand-new database file and copies rows into it, so the output always has `journal_mode = delete` (rollback mode, header bytes `18–19 = 1`). Because `equal.LogicalPragmas` includes `journal_mode`, `E3` compares `rollback` against `wal` and reports `false`, while every other logical component matches (`E3-except-journal_mode yes`), and running `VACUUM INTO` on the source produces a byte-identical canonical file (`E1-after-VACUUM-INTO yes`).

3. **Process kill at `FULL` `fsync #3` and the reader-pinned `NORMAL` power-cut model.**
   - In `synchronous=FULL`, SQLite writes all frames of step `4` (including its commit frame) to `r.db-wal` via `pwrite64` **before** calling `fsync` (`src/wal.c:4196-4213`). Killing the writer process with `SIGKILL` on entry to `fsync #3` leaves those completed `pwrite64` bytes intact in the OS kernel page cache; the writer never got to print `ack 4`, so `acknowledged = 3`, while the next open runs `walIndexRecover` (`src/wal.c:1390-1614`) and recovers **step 4** (`acknowledged + 1`).
   - In the uninterrupted `NORMAL` run without a reader, the `PASSIVE` checkpoint copied all `74/74` frames, synced `.db`, and step `8` restarted the WAL, whose 32-byte header sync (`src/wal.c:4121-4124`) was the last `-wal` sync (`cut = 32`). With a reader pinned at step `5`, `walCheckpoint` (`src/wal.c:2233-2251`) capped `mxSafeFrame` at `36` of `74` frames, so the WAL could **not** restart and steps `8–11` stayed in the same WAL generation. The last `-wal` sync was therefore the checkpoint's own pre-backfill WAL sync (`src/wal.c:2277`), which synced all frames up to step `7`'s commit end (**byte `304,912`**).
   - Because `mxSafeFrame < mxFrame`, `walCheckpoint` skipped syncing `.db` (`src/wal.c:2328-2335`), leaving `15` unsynced writes in `.db`. Those unsynced writes do not break recovery because every page they modified had already been synced into `-wal` at line `2277` first; whether `.db` keeps all `15` writes or keeps none (the pre-checkpoint `.db`), `walIndexRecover` serves those pages from the synced `-wal` and recovers **step 7** with `integrity_check ok`.

4. **`PRAGMA integrity_check` vs `PRAGMA quick_check` and `"row 66"` vs `rowid = 76`.**
   - `sqlite3BtreeIntegrityCheck` (`src/btree.c:11144-11295`) checks structural invariants (page headers, cell pointers, fragmentation, key ordering, overflow chains, freelist reachability) and never validates the semantic content of unindexed columns (`events.note`) or inspects the body of freelist leaf pages, so both return `ok`.
   - Table-to-index cross-checks are generated separately in `src/pragma.c` only when `!isQuick` (`src/pragma.c:2058`). `PRAGMA quick_check` skips them, so it returns `ok` even when `events.account_id` in the table disagrees with `events_by_account`, whereas `PRAGMA integrity_check` flags the mismatch.
   - During `PRAGMA integrity_check`'s table scan, register `7` is incremented by `1` for every row visited (`OP_AddImm 7, 1`, `src/pragma.c:1850-1857`), and `integrityCheckResultRow` (`src/pragma.c:2084-2090`) formats that 1-based scan counter—not the table's `rowid`—into `"row N missing from index X"`. Because earlier deletes left gaps in `events` rowids, `rowid = 76` was the `66`th row scanned.

5. **`internal/walship`: lock-safe `-wal` reads, slot-0 read marks, and no-WAL resume.**
   - **Lock-safe `-wal` reads:** SQLite places POSIX advisory locks (`fcntl`, Chapter 6) on the `.db` file and on `-shm`, never on `-wal`. Opening and closing `-wal` via `os.ReadFile` in the same process therefore releases zero POSIX locks (proven by unit test `TestReadingTheWALInAProcessWithAConnectionKeepsItsLocks` in `internal/walship/walship_test.go`, whereas a stray close of `-shm` dropped the write lock).
   - **Slot-0 read mark and WAL restarts:** After `Shipper.Cycle` ships every committed frame and runs its own `PASSIVE` checkpoint, if `nBackfill == mxFrame`, `takePin` acquires read-lock **slot `0`** (`walTryBeginRead`, `src/wal.c:3020-3272`). Slot `0` does **not** block `walRestartLog` (`src/wal.c:3875-3915`, which locks slots `1–4` only), so the next writer restarts the WAL—which is safe because every frame of the old generation was already shipped and backfilled (`nBackfill == mxFrame`). Meanwhile, slot `0` **does** block any subsequent checkpoint from backfilling new unshipped frames because backfilling requires an exclusive lock on slot `0` (`src/wal.c:2259-2260`).
   - **Hashing pages on no-WAL resume:** When the last shipped position had no WAL (`Generation.None()`) and the live database also has no WAL after the shipper was stopped (`!s.continuous`), comparing `current == s.wal.Generation` (`"" == ""`) proves nothing—offline commits may have been written, checkpointed, and their `-wal` deleted on last close. `Shipper.classify` therefore reads every live page via `ReadPages` and compares `SHA256Hex(image)` against `s.state`; any mismatch triggers a discontinuity snapshot instead of replaying later WAL frames onto a stale image.
